**第二期（未开始）**：今日宜发（农历库、每晚 0 点的定时任务、平台管理端编辑、品牌库跳转）。下文「今日宜发」一节仍是设计。

第一期实现与下文设计不同的地方：

- 模型：文案单独配模型 `COPY_WRITER`（`COPY_WRITER_URL`、`COPY_WRITER_API_KEY`、`COPY_WRITER_MODEL`，正式服用 OnlyRouter 的 gpt-6-luna），其他模块的模型不变。
  不单独配时退回平台文本模型 `TEXT_WRITER`。单独配的原因：正式服的 `TEXT_WRITER` 是 deepseek-v4.1-flash，不能看图，但约 0.7 秒就能回答，直播弹幕回复靠它；gpt-6-luna 能看图，一次要 5–20 秒，不能拿去顶替直播用的模型。
  两者请求格式相同，`CopyWriterAdapter` 直接复用 `ChatCompletionTextAdapter`。看图和写稿在**同一次调用**里完成；为此 `ChatCompletionTextAdapter` 加了两个可选参数：`images`（最多 6 张 JPEG data URL）和 `jsonObject`（要求返回 JSON 对象），不传时请求和原来完全一样。退回 `TEXT_WRITER` 时如果那个模型不能看图，带图的文案生成会失败。
- AI 味：由写稿的同一次调用自评打分（`aiScore`、`aiReason`），没有用 `TEXT_REVIEWER`。
- 素材：支持上传图片和作品库图片，合计最多 6 张；**视频暂不支持**。
- 校验：词表放在文案模块内（`CopyGuard`），没有抽到 `common/`。不合格的条目带原因补写一次，最后至少 2 条合格才算成功并扣费，否则整批失败退回烟火。
- 商品：提交时把所选商品的价格、规格、优惠、卖点存成快照（`copy_batches.product_facts`），生成和改写都以快照为准。
- 改写不收费，每批最多 5 次；改写失败不占次数。口吻样本每家店每天最多更新 10 次。

页面稿（Artifact，仅作者可见）：https://claude.ai/artifact/PD1dLQvTvCH3X56GH9zXFf ，包含「首页 · 今日宜发」和「工作区 · 生成与预览」两张画板。页面稿里的文案、AI 味分数和门店志条目都是示意，不代表模型输出。

## 要解决的问题

商家拍了照片、剪了视频，或者只是有件事想说，但不知道发朋友圈、抖音、小红书该配什么字。他们用通用 AI 写文案，主要卡在三件事上：

1. 一看就是 AI 写的；
2. 不知道发出去是什么样子；
3. 今天不知道该发什么。

文案创作的定位是「懂这家店的文案助手」。它和通用写作工具的区别来自一方志已有的数据：门店、品牌库、商品库、作品库，以及发布过的内容。文案能用真实的店名、地址和营业时间，商家不用每次重新交代。

## 页面

入口：侧栏「内容工具 → 文案创作」，路由 `/copy`（首页）和 `/copy/create`（工作区）。

### 首页 `/copy`

- **今日宜发黄历卡**：显示日期和节气，「宜」列 2–3 条，「忌」列 1–2 条。内容来自当天的行业黄历，见下文「今日宜发」。
- **今天可以发**：3 个选题，每个带平台和风格。点「就写这个」进入工作区，并预填选题、平台和风格。
- **我的口吻**：已学会时显示口吻摘要和特点标签；没学过时显示「喂几条你以前发的朋友圈」的入口。
- **门店志**：最近的定稿记录。
- 右上角「直接写一条」进入空白工作区。

### 工作区 `/copy/create`

三栏布局，窄屏时按顺序堆叠。

- **左栏（设置）**
  - 发到哪：朋友圈 / 抖音 / 小红书。
  - 发什么：上传图片或视频，或从作品库选，最多 9 张图或 1 个视频；一句话（可选）；关联商品（可选）。
  - 风格：真诚日常、文艺治愈、幽默玩梗、干货种草、高级简约、热情福利。
  - 带上店铺：不提 / 轻提 / 引导到店。
  - 学我口吻开关；生成按钮。
- **中栏（结果）**：3 条文案。
  - 每条显示写法名称（如「场景描写」）和 AI 味指数。
  - 「为什么这么写」默认收起。
  - 操作：改写（更短、更口语、换个开头、去 AI 味）、复制、定稿。
  - 抖音和小红书的标题、正文、话题分区显示；复制时合成一段，按平台习惯排版。
- **右栏（发出去的样子）**：手机预览，显示中栏选中的那条。
  - 朋友圈：头像、文字、配图。
  - 抖音：竖屏画面，底部叠加标题、正文和话题。
  - 小红书：双列信息流中的封面卡片。
  - 预览用商家自己的素材和店名渲染，是简化的示意样式，不照搬平台界面。
- **定稿**：盖一个朱砂「定稿」方印（遵守 `prefers-reduced-motion`），同时复制到剪贴板、写入门店志。

### 创作记录

每次生成都自动存成一条记录，不需要商家手动保存。

- **入口**：工作区结果栏右上角的「创作记录」，首页右上角也有一个。首页的入口直接进工作区，并打开记录抽屉。
- **形式**：右侧抽屉，跟视频反推的「反推历史」一样（`vs-drawer`）。不另开页面，看完关掉就回到当前创作。
- **列表**：
  - 按天分组（今天、昨天、具体日期），最新的在上面；
  - 每条显示：素材缩略图（只有一句话的显示「文」字块）、第一条文案的开头、平台 · 风格 · 时间；
  - 有定稿的显示小「定」印，正在看的那条标「当前」；
  - 生成中的显示进度，失败的显示「生成失败，1 烟火已退回」；
  - 顶部可以按平台筛选：全部 / 朋友圈 / 抖音 / 小红书。
- **打开一条**：左栏恢复成那次的设置（平台、素材、一句话、风格、带店程度、口吻开关），中栏显示那次的 3 条，改写过的显示最新版本，手机预览跟着走。打开之后可以接着改写、复制、定稿：改写的计费和次数上限跟在当场生成时一样（见「计费」）；点「换一批」或改了设置再生成，算一次新的生成，收 1 烟火。
- **素材已删除**：缩略图位置留空并标「素材已删除」，文案照常显示。这跟视频方案的做法一致。
- **离开再回来**：生成中离开页面，回来后继续等待，完成后自动打开那批结果。做法照视频方案：按标签页记住批次 ID。
- **谁能看**：同一门店的成员都能看到这家店的记录。别人创建的记录显示创建人。
- **保留**：第一期不自动清理，也不提供删除。

**和门店志的区别**：创作记录是草稿池，存的是每次生成的全部结果；门店志只收定稿的那一条，是这家店真正要发、发过的内容。

### 交互上的规矩

- 说明性的小字尽量少。思路、合规提示只在需要时出现，不常驻。
- 文案中有两种占位标记：
  - `〔店名〕`：取自门店资料。界面上用点线下划线标出，复制时替换成真实值。
  - `【几】`：资料里没有、需要商家补。界面上用朱砂色字加虚线下划线标出。复制或定稿时，如果还有未补的 `【】`，先提示商家。

## 生成链路

一次生成是一个异步任务。按仓库约定走 `tasks` 表 + `TaskHandler`，结构参照 `video/plan`。

```
素材 ──► 理解（VISION_ANALYZER）──► 画面描述 ─┐
门店 / 品牌 / 商品事实 ──────────────────────┼─► 写作（TEXT_WRITER）──► 校验 ──► 3 条文案
口吻档案、平台规则、风格、带店程度 ──────────┘          ▲                │
                                                       └── 不通过重写一次 ┘
```

1. **理解素材**：`TEXT_WRITER` 当前的适配器（`ChatCompletionTextAdapter`）只发送纯文本，不能看图。看图走已有的 `VISION_ANALYZER` 能力，现由 `VideoAnalysisHttpAdapter` 提供。它目前只接收 `data:image/jpeg;base64` 图片，并要求返回 JSON。
   - 图片：转成 JPEG 后交给它，输出一段客观的画面描述：场景、主体、氛围、可见文字。
   - 视频：复用 `video/analysis` 的 `VideoFrameExtractor` 抽取少量关键帧。第一期不分析音轨。
   - 只有一句话、没有素材时跳过这一步。
   - 画面描述只用来理解画面，不能作为商家事实。图里看到的价格牌不能当成真实价格写进文案。
2. **写作**：`TEXT_WRITER` 一次输出严格 JSON，包含 3 个版本。每个版本有写法名称、思路、标题（抖音、小红书）、正文、话题。输入是：画面描述、一句话、门店与品牌事实、所选商品事实、口吻档案、平台规则、风格、带店程度、最近 10 条门店志摘要（用来避免重复）。
3. **校验**：见「事实与合规」。不通过时，带上原因重写一次；仍不通过的版本标为失败，不展示。
4. **AI 味评估**：对通过校验的版本各打一次分，见下文。

改写（更短、更口语、换个开头、去 AI 味）是对单条文案的一次 `TEXT_WRITER` 调用，同样经过校验，结果作为这条文案的新版本保存。

## 学我口吻

- **样本**：商家粘贴 3–10 条自己发过的文案，或从门店志里勾选。按门店保存，不跨门店共享。
- **口吻档案**：样本更新时调用一次 `TEXT_WRITER`，总结口吻特点：常用词、句长、标点习惯、称呼、语气词、有没有 emoji。档案保存为结构化 JSON，首页展示用的特点标签也来自这里。
- **冷启动**：没有样本时，用门店所属品牌的 `languageStyle`（品牌库已有字段）作为起点。两者都没有时，按通用写法生成。
- **生成时**：口吻档案和最多 3 条原始样本作为示例放进提示词，不训练模型。
- **边界**：样本里的事实（价格、活动）不得带进新文案。样本只用来模仿语气。

## AI 味指数

- 对每条文案打 1–5 分，分别对应低 / 中 / 偏高。由 `TEXT_REVIEWER` 能力评分，并给出主要原因（如「套话多」「排比工整」「感叹号密集」）。
- 3 分及以上时显示「去 AI 味」入口。
- 这个分数是模型的主观估计，界面上只显示等级，不写成「检测」「准确率」之类的说法。
- `TEXT_REVIEWER` 目前没有适配器。第一期可以先登记到 `ChatCompletionTextAdapter` 上，与写作共用同一个模型，以后再拆开。

## 今日宜发

### 判定依据：三层信息

1. **行业**：取门店所属品牌的 `industry`。品牌库页面把它做成必选下拉（`src/views/BrandsView.vue` 的 `industryOptions`），选项是：

   餐饮 / 茶饮、美妆 / 个护、服饰 / 鞋包、家居 / 生活方式、教育 / 服务、科技 / 互联网、其他。

   行业黄历直接按这 7 个选项生成，不另设分类，也不用模型推断。
2. **时令**：公历日期、星期、农历、节气、法定节日、常见营销节点。
3. **店铺自身**：商品库最近上新的商品、正在供的联盟券、门店志的发布记录（多久没发某类内容、上一条发了什么）。

### 行业判断不了时：引导去品牌库完善

以下情况视为「判断不了」：

- 门店没有关联品牌；
- 品牌的 `industry` 为空。页面上是必选，但后端 `BrandDtos` 只限制长度、不要求必填，旧数据和自动创建的默认品牌可能为空；
- 选的是「其他」；
- 值不在上面 7 个选项里（选项改版前留下的自由文本）。

这时：

- 黄历卡改用只按节气和日期生成的通用黄历，「今天可以发」照常按商品库和门店志生成；
- 黄历卡底部（宜 / 忌下面，原来放一句时令短语的位置）换成一行提示和一个按钮：
  - 店长（`auth.isOwner`）看到「补充行业，推荐更贴合你的店」和「去品牌库完善」按钮。按钮跳到 `/brands`，直接打开这个品牌的编辑弹窗，并定位到「品牌识别」。没关联品牌时，按钮改为「去品牌库关联品牌」；
  - 员工看不到按钮，只看到「请店长在品牌库补充行业」。`isOwner` 只决定显示什么，能不能改品牌以后端权限为准；
- 这个提示只出现在黄历卡上，工作区不打扰。商家补完行业回到首页时，重新取当天对应行业的黄历，不用等到第二天；
- 行业已识别时，黄历卡左上角显示「按 餐饮 / 茶饮」，让商家知道推荐依据是什么。

品牌库这边需要配合一处小改动：`BrandsView` 目前只能在页面里点「编辑档案」打开弹窗，要支持通过路由参数（如 `/brands?edit=<品牌ID>&section=identity`）直接打开。品牌模块有自己的负责人，改动前先商量。

现有 7 个选项比较粗：美容美发、健身、鲜花、宠物、酒店民宿等都会落到「其他」，只能拿到通用黄历。要细化，就得改品牌库的选项，这会影响品牌模块和已有数据，单独评估。

### 谁算、谁写

- **日期事实由代码计算**：农历、节气、节日用开源农历库计算（候选：6tail 的 lunar-java，引入前确认版本、许可证和覆盖年份），不让模型推日期。法定节假日安排每年由国务院公布，按年维护成配置。
- **行业解读由 AI 写**：模型拿到确定的日期事实和行业，写出当天的「宜 / 忌」与 3–5 个选题方向。
- **门店级内容由 AI 写**：行业黄历结合门店事实，写出「今天可以发」的 3 个具体选题。

### 定时与任务

时区固定为 `Asia/Shanghai`。定时器只负责登记任务，写法照 `alliance/AllianceStatementScheduler`。

| 时间 | 任务 | 幂等键 | 调用量 |
| --- | --- | --- | --- |
| 每天 0:00 | 品牌库的 6 个具体行业各生成一份，再加一份通用黄历（给「其他」和判断不了的门店） | `almanac:<日期>:<行业>` | 7 次 |
| 0:00–6:00 分批 | 为最近 7 天活跃过的门店生成「今天可以发」 | `almanac-store:<日期>:<门店>` | 按活跃门店数，错开提交 |
| 商家打开首页时 | 不活跃的门店现场生成，生成后缓存 | 同上 | 按需 |

### 兜底与保护

- 某个行业的黄历生成失败：显示只用日期事实的通用版本，不留空，也不显示前一天的内容。
- 行业判断不了：见上文「行业判断不了时」。
- 敏感日期写死规则，不依赖模型自觉：清明、国家公祭日等日子，「忌」里必须包含喜庆促销，选题方向也不出现促销。
- 「忌」按行业带上合规提醒，例如：美妆 / 个护忌写功效和使用前后对比；教育 / 服务忌承诺提分、包过；餐饮 / 茶饮忌用「最」「第一」，忌暗示保健功效。
- 「宜 / 忌」只是内容建议，不涉及命理吉凶。
- 平台管理端可以查看当天的行业黄历，也可以直接修改。不强制每天审核。

## 门店志

- 定稿时写入一条记录：平台、最终文本（商家改过的以改后为准）、来源生成批次、定稿时间、操作人。
- 首页显示最近几条，另有完整列表页。
- 门店志会作为后续生成的输入（避免重复），也可以选作口吻样本。
- 第一期不做连载建议和年鉴，但数据结构要能支持按时间、平台、主题回看。

## 事实与合规

- **事实来源**：只有商家输入的一句话、门店资料、品牌库、所选商品算事实。画面描述、口吻样本、门店志旧文案都不算。
- **数字校验**：标题和正文里出现的价格、折扣、日期、数量，必须能在事实中找到，否则视为不通过。思路参照 `ImagePlanner` 的「文案包含用户未提供的数值」和 `live/script/ScriptGuard.violation(text, facts)`。
- **用词校验**：极限词（全网最低、史上最、国家级、第一等）和未经事实支持的促销承诺（半价、免单、限时等）视为不通过。`ScriptGuard` 里已有这两份词表，但它的清洗规则是为口播写的：会去掉 emoji 和列表符号，与小红书的排版冲突。所以只复用词表，不复用清洗逻辑。词表抽到 `common/` 需要双方审查；也可以先在模块内放一份，二选一，实现前定。
- **行业附加规则**：美妆 / 个护、教育 / 服务、餐饮 / 茶饮等行业有额外禁用说法，与「忌」用同一份配置。
- **占位符**：缺少的事实由模型输出 `【…】`，不让它编；门店字段输出 `〔店名〕〔地址〕〔营业时间〕` 等固定占位，由后端替换成真实值，模型不直接写门店字段的值。

## 后端

新模块 `com.wuyao.growth.copywriting`，结构照 `asset/` 写。跨模块只调用公开的 Service/DTO：门店、品牌、商品、素材、作品、计费。

### 表

Flyway 版本号在实现时同步主干后登记，这里不预先编号。除 `copy_almanacs` 外，每张表都带 `tenant_id`，并且 `ENABLE / FORCE ROW LEVEL SECURITY` + 租户策略。

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `copy_batches` | 一次生成（创作记录） | `store_id`、`request_key`（幂等）、`platform`、`style`、`store_level`、`voice_on`、`asset_ids`、`work_ids`、`product_ids`、`note`、`topic`、`status`、`task_id`、`billing_reservation_id`、`vision_summary`、`versions`（JSONB，含改写历史）、`error_message` |
| `copy_journal_entries` | 门店志 | `store_id`、`batch_id`、`version_index`、`platform`、`title`、`body`、`tags`、`finalized_by`、`finalized_at` |
| `copy_voice_profiles` | 口吻档案 | `store_id`（唯一）、`samples`（JSONB）、`profile`（JSONB）、`updated_at` |
| `copy_store_almanacs` | 门店当天的「今天可以发」 | `store_id`、`date`、`topics`（JSONB）、`status`；唯一键 `(store_id, date)` |
| `copy_almanacs` | 行业黄历（平台级） | `date`、`industry`（品牌库选项或 `通用`）、`facts`（JSONB）、`good`、`avoid`、`directions`、`edited_by`；唯一键 `(date, industry)` |

`copy_almanacs` 不属于任何租户。参照 `billing_plans`，这张表不加租户策略，应用账户只能读。由谁来写（worker 用什么账户、管理端怎么改）实现前和 `common/`、`iam/` 的负责人确认。

### 任务

| 类型 | 触发 | 说明 |
| --- | --- | --- |
| `COPY_GENERATE` | 用户点生成 | 理解素材 → 写作 → 校验 → AI 味评分 |
| `COPY_REWRITE` | 用户点改写 | 单条改写 + 校验 + 评分 |
| `COPY_VOICE_PROFILE` | 样本更新 | 总结口吻档案 |
| `COPY_ALMANAC_INDUSTRY` | 每天 0:00 定时登记 | 每个行业一条 |
| `COPY_ALMANAC_STORE` | 0:00–6:00 分批，或首页现场触发 | 每个门店一条 |

所有 Handler 按至少执行一次来设计：模型调用可以重复，写库按幂等键覆盖；计费沿用预占 → 成功扣除 / 失败退回。

租户和用户只从 JWT 取。`storeId` 由后端校验当前用户有没有权限。

## 计费

**已定**：每次生成文案收 **1 烟火**，与视频方案相同。

- 一次生成包含看图、写 3 条、校验和 AI 味评分，整体算一次；只写一句话、不传素材也收 1 烟火。
- 流程照现有写法：发起时预占，成功后扣除，失败或取消退回。预占键为 `copy-generate:<requestKey>`，计费类型 `COPY`。
- 价格先照 `BillingService` 现有常量的写法，加一个 `COPY_CREDITS = 1`。
- 页面上生成按钮写「生成文案 · 1 烟火」。

**建议，待确认**：

| 环节 | 建议 |
| --- | --- |
| 改写（更短、更口语、换个开头、去 AI 味） | 不单独收费，每次生成最多改写 5 次 |
| 口吻档案 | 免费，限制每天更新次数 |
| 今日宜发（行业黄历、今天可以发） | 平台承担，不向商家收费 |
| 非会员 | 能看今日宜发；点生成时与其他生成功能一样，提示开通会员（`requireMembership`） |

平台要承担的成本里，只有「今天可以发」会随商家数量增长：活跃门店数 × 每天 1 次文本调用。

## 验收标准

- 三个平台各生成一次，每次得到 3 条写法不同的文案；抖音和小红书都有标题和话题。
- 关闭「带上店铺」时，文案里不出现店名、地址；选「引导到店」时，出现真实店名和地址，没有遗留 `〔〕` 占位。
- 输入里没有的价格、日期，文案里不出现。人为构造模型输出编造数字的测试，校验应拦截。
- 打开学我口吻，生成结果在样本特征（如「咱家」、句尾「～」）上明显靠近；样本里的价格不出现在新文案中。
- 0:00 的定时任务对同一天重复执行，不产生重复的行业黄历；某行业生成失败时，首页显示通用版本。
- 门店品牌行业为空、为「其他」或没关联品牌时：首页显示通用黄历；店长看到按钮，点击后进入品牌库并打开该品牌的编辑弹窗；员工只看到提示。补完行业回到首页，显示对应行业的黄历。
- 清明当天，任何行业的「宜」和选题里都不出现促销。
- 定稿后，门店志新增一条记录；同一条再次定稿不重复写入。
- 生成后关掉页面再回来，生成中的批次继续等待并自动打开；从创作记录打开一条旧批次，左栏设置和中栏 3 条都恢复；接着改写不扣费。
- 生成成功扣 1 烟火；生成失败或取消，预占的 1 烟火退回；同一个 `requestKey` 重复提交只预占一次。
- 后端改动跑 `mvn verify`，前端跑 `npm test && npm run lint && npm run typecheck && npm run build`。
