# 邀请返利 · 一代直推、充值返现金

> **状态：分两期。第一期已上线（迁移 V71、V72）；第二期提现在分支 `claude/referral-withdrawal` 实现（迁移 V73），尚未上线。**
> 第一期：实名核验通过后领邀请码、带码注册归属、充值和开通会员记返利（冻结 7 天）、「我的邀请」页面、后台邀请关系 / 返利明细 / 推广人排行 / 返利比例、《推广协议》。
> 第二期：本人银行卡四要素核验绑卡、申请提现、后台提现审核（查看收款信息留审计、驳回、登记代扣税额和转账流水）、作废返利与已提现返利的扣回。
> 后端由 `ReferralIntegrationTest`、`AliyunIdentityVerifierTest` 覆盖，阿里云银行卡核验在测试里是模拟的，**还没有用真实接口调用过**；页面在本地预览里用模拟接口走查过。
> 《推广协议》上线前需法务确认，§9 列出还没定的事。

## 1. 规则一句话

每个用户有一个专属邀请码。新商家通过邀请链接注册，就永久归属到邀请人；没有邀请码的归属公司。
被邀请商家每次**充值烟火**并实际到账，邀请人按比例得到**现金**返利，过冻结期后可申请提现，由平台人工打款。

| 项目 | 规则 |
| --- | --- |
| 层级 | 只有一级。邀请人的邀请人不分钱 |
| 成为推广人 | 不收任何费用；实名核验通过、同意《推广协议》即可领码 |
| 计算基数 | 充值烟火（`TOPUP`）和开通会员（`MEMBERSHIP`）订单的实付金额，比例分开设：充值默认 10%，开通会员默认 20%（V72）；赠送烟火、运营手动开通的会员不算 |
| 比例 | 平台统一比例，默认 10%，平台运营在管理后台调整；每笔返利记下当时的比例 |
| 期限 | 终身有效 |
| 冻结期 | 充值到账后 7 天，期间退款则返利作废 |
| 提现 | 本人实名通过、绑定本人银行卡（四要素核验）、可提现金额减去待扣回满 100 元，一次提走全部，平台审核后人工网银转账 |
| 归属 | 注册时一次绑定，之后不改 |

只做一级、不收入门费，不落入《禁止传销条例》的情形，也不属于微信禁止的多级诱导分享。

## 2. 流程

```
邀请人                         被邀请人                        平台运营
──────                         ────────                        ────────
① 实名核验通过，打开「我的邀请」
   同意《推广协议》，拿到邀请码、链接、二维码
         │ 分享
         ▼
                          ② 打开链接 → 短信或微信登录
                             新手机号注册时绑定到邀请人
                             （已有账号不受影响）
                                    │
                          ③ 充值烟火，支付到账
                                    │
④ 出现一条「冻结中」返利    ←───────┘
   7 天后变为「可提现」
         │（以下为第二期）
⑤ 绑定本人银行卡（四要素核验）
   满 100 元，申请提现      ─────────────────────────────→  ⑥ 查看完整收款信息（写用途，留审计）
                                                              公司网银转账，登记代扣税额、流水号、打款日期
⑦ 提现单变为「已打款」，    ←─────────────────────────────┘    或驳回，返利回到可提现
   显示代扣税额和实发金额
```

## 3. 邀请码与绑定（第一期已实现）

### 3.1 邀请码

- 每个用户一个，包括店员。实名核验通过、打开「我的邀请」并同意协议时生成。
- 8 位，去掉容易看错的 `0 O 1 I L`，全局唯一，不可修改。
- 链接：`/login?mode=register&invite=<邀请码>`。邀请码不含个人信息，可以放在链接里。

### 3.2 前端带码

- 登录页读到 `invite` 参数后存入 localStorage，保留 30 天，登录成功后清掉。
  微信登录要跳出再回来，参数会丢，所以必须先存。
- 短信登录和微信登录请求都带上 `inviteCode`；后端只在**新建用户和商家账户**时使用它。
- 登录页显示所用邀请码，并提示邀请人能看到打码后的手机号、注册时间和充值返利记录。

### 3.3 绑定规则

- 新建用户时 `iam` 发出 `UserRegistered` 事件，`referral` 在注册事务提交后绑定；绑定失败只记日志，账号归属公司，不影响注册。
- 邀请码不存在、邀请人账号已停用：不报错，归属公司。
- 已有账号点链接登录：不改归属。
- **归属公司就是不写邀请人**，不建虚拟的公司用户。上线前的老账户全部视为归属公司，不回填。
- 店员账号由管理员创建，不经过注册，不产生归属。

## 4. 返利（第一期已实现）

### 4.1 怎么产生

1. 充值或会员订单变为已支付（微信、支付宝回调或运营人工确认，都汇到 `BillingService.fulfil`），`billing` 发出 `OrderPaid` 事件（带订单类型）。
2. `referral` 在入账的同一事务里登记任务 `REFERRAL_COMMISSION`，幂等键 `referral-commission:{订单号}`；没有邀请人的不登记。
3. `TaskHandler` 按此刻的平台比例，在邀请人所在商户写一条返利，`order_id` 唯一，重复执行只有一条。

返利金额 = `floor(实付分 × 比例万分点 / 10000)`，单位分。

### 4.2 状态

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 冻结中 | `PENDING` 且 `available_at` 未到 | 到期自动算可提现，不需要定时任务 |
| 可提现 | `PENDING` 且 `available_at` 已过，没有提现单 | 随下一张提现单带走 |
| 提现审核中 | `withdrawal_id` 有值，`withdrawn_at` 为空 | 驳回则清空 `withdrawal_id` 回到可提现 |
| 已提现 | `withdrawn_at` 有值 | 运营作废后变成欠款 |
| 已作废 `VOIDED` | 运营作废，必须写原因，推广人能看到 | 终态 |

- 当前没有退款入口（见 `yanhuo-billing-decisions.md`），被邀请商户退款后由运营在「返利明细」手动作废对应返利。
- 提现审核中的返利不能直接作废，要先驳回那张提现单。
- 已提现的返利作废后记为欠款（`VOIDED` + `withdrawn_at` 有值 + `clawback_withdrawal_id` 为空），
  下一张提现单申请时一并扣回并记上 `clawback_withdrawal_id`；可提现减欠款不满 100 元就不能提，欠款一直挂着。

## 5. 提现（第二期，V73）

### 5.1 收款银行卡（`community` 模块 `bank_cards`）

| 字段 | 说明 |
| --- | --- |
| 类型 | 个人银行卡，一人一张，换卡直接覆盖 |
| 户名 | 就是本人实名：姓名、身份证号从 `real_name_applications`（必须 `VERIFIED`）解密，用户不用填 |
| 核验 | 阿里云 `BankMetaVerify`，`BANK_CARD_4_META`：卡号 + 姓名 + 身份证号 + 银行预留手机号。`bizCode` 1 一致才保存；2 不一致、3 查无记录都按不一致；其他一律算暂时无法核验，不保存 |
| 限次 | 滚动 24 小时内不一致满 3 次就停到第二天（和实名一样按审计表计数） |
| 存储 | 卡号用 `RealNameCrypto` 加密（字段名 `bank-card`），只显示开户行和后 4 位；预留手机号只用于核验，不保存 |
| 同意 | 实名说明写明资料只用于实名审核，所以绑卡页面单独勾选同意把实名信息用于银行卡核验 |

不做人工审核。核验一致、不一致都记进平台管理审计表（`BANK_CARD`），带核验请求号。

### 5.2 提现单（`referral_withdrawals`）

- 一次申请把当前**全部可提现**返利打包进一张提现单，不支持部分提现。这样不用另做余额账本，
  提现金额 = 可提现返利之和 − 待扣回欠款，满 100 元才能申请。
- 申请时把收款卡抄一份快照（开户行、卡号密文、后 4 位）到提现单上，之后换卡不影响这一单，所以待审核期间不禁止换卡。
- 同一个人同时只能有一张待审核的提现单（部分唯一索引）。申请时锁住账号和相关返利行，和作废互斥。
- 每次申请都要勾选同意当前版本的《推广协议》（含扣回规则），版本号记在提现单上。

| 状态 | 谁操作 | 说明 |
| --- | --- | --- |
| 待审核 | 推广人提交 | |
| 已驳回 | 运营 | 填原因，带走的返利回到可提现，扣回的欠款回到待扣回 |
| 已打款 | 运营 | 公司网银转账后填代扣税额、流水号、打款日期；实发 = 提现金额 − 代扣税额，由系统算出 |

打款前运营点「查看收款信息」，要写用途，返回户名（本人实名）、开户行和完整卡号，记审计（`REFERRAL_WITHDRAWAL` / `REVEAL`）。

### 5.3 个税

给个人付推广费按劳务报酬，平台需要预扣预缴个税并申报。系统只记录提现金额、代扣税额和实发金额，
**税额由财务按规定算好后填入，系统不自己算**，避免口径错误。也可以改走第三方灵活用工平台代发，见待定 7。

## 6. 防刷（第二期）

- 冻结期 + 退款作废，挡住「充值拿返利再退款」。
- 提现审核时，运营能看到每笔返利对应的被邀请商家注册时间和充值时间。
  短时间内大量新账户首充、或被邀请人与邀请人是同一实名，运营驳回或作废。
- 自动判断「同一实名」需要实名表提供不可逆的身份证号指纹（HMAC），现在只有随机 nonce 的密文，
  对比不了。是否在 `community` 模块加这一列见待定 8；不加则靠人工审核。

## 7. 页面

### 7.1 我的邀请（用户，第一期已实现）

- 未实名：提示先去实名核验。
- 已实名未领码：显示规则和《推广协议》，同意后生成邀请码。
- 已领码：邀请码、复制链接、二维码。
- 汇总：已邀请商户数、冻结中、可提现。
- 提现（第二期）：本次可提现、待扣回；绑定或更换本人银行卡；申请提现（确认金额和收款卡，勾选协议）；
  提现记录（金额、扣回、收款卡、状态、代扣税、实发、打款日期或驳回原因）。
- 返利明细：到账时间、被邀请商户（打码手机号）、充值金额、比例、返利金额、状态；作废的显示原因。
- 邀请的商户：打码手机号、注册时间。

### 7.2 运营后台

- 第一期：「邀请返利」页四个标签：邀请关系（每个商户归在谁名下，没有邀请人的显示「公司」）、返利明细（按邀请人、状态筛选，带冻结中 / 可提现合计）、
  推广人排行（按返利合计排序）、返利比例（充值和开通会员分开调整，0–50%，必须写原因）。数据逐个商户只读汇总，每个商户最多取最近 2000 笔返利。
- 第二期：返利明细加「作废」（写原因；已提现的作废后从下次提现扣回）；新标签「提现审核」：按状态筛选，
  显示待审核笔数和金额，待审核的可以查看收款信息、登记打款、驳回。操作沿用联盟对账单的弹框输入。
  待审核提现计入管理后台的待办数，侧栏「邀请返利」显示角标。

## 8. 系统设计

### 8.1 跨商户

邀请人和被邀请人是两个商户，数据按归属分开放，各自行级隔离。数据库连接在事务开始时绑定商户，
所以跨商户写入用 `TenantContext.runAs` 切到目标商户后新开事务（`REQUIRES_NEW`）：

- 被邀请商户里存「我的邀请人是谁」，只有编号，不带对方个人信息，供算返利时查。
- 邀请人商户里存邀请码、被邀请商户列表、返利、提现单；本人银行卡也在本人商户。
- 平台审核提现、作废返利时切到推广人所在商户执行。

### 8.2 数据表（V71）

新模块 `referral/`。

| 表 | 属于 | 主要字段 |
| --- | --- | --- |
| `referral_codes` | 邀请人 | 用户（主键）、邀请码（全局唯一）、协议版本、同意时间 |
| `referral_attributions` | 被邀请人 | 商户（主键）、邀请人用户、邀请人商户、所用邀请码、绑定时间 |
| `referral_invitees` | 邀请人 | 被邀请商户（主键）、邀请人用户、脱敏手机号、注册时间 |
| `referral_commissions` | 邀请人 | 邀请人用户、被邀请商户、订单（唯一）、实付分、比例万分点、返利分、状态、可提现时间 |
| `referral_rates` | 平台 | 比例万分点、调整原因、操作人、时间；只增不改，最新一行生效，和 `billing_plans` 一样不分商户 |
| `bank_cards`（V73） | 本人 | 用户（主键）、开户行、卡号密文、后 4 位、核验时间 |
| `referral_withdrawals`（V73） | 邀请人 | 返利合计、扣回、提现金额、状态、收款卡快照、协议版本、驳回原因、代扣税、实发、流水号、打款日期 |

V73 给 `referral_commissions` 加了 `withdrawal_id`、`withdrawn_at`、`clawback_withdrawal_id`、`void_note`、`voided_by`、`voided_at`。

注册时按邀请码查人要跨商户，用 SECURITY DEFINER 函数 `referral_code_owner(code)`，只返回用户编号、商户编号和账号是否有效。

## 10. 验收要覆盖的情况

第一期（已覆盖）：

- 未实名不能领码；不勾协议不能领码；重复领码返回同一个码。
- 带码注册归属邀请人（大小写都认）；无码、错码归属公司；同一次注册重复处理不多写。
- 同一订单任务重复执行，只有一条返利；没有邀请人的商户充值不登记任务。
- 冻结期内算冻结中，过期算可提现。
- 只有平台运营能调比例，超过 50% 被拒；调整后新到账的充值按新比例。
- 被邀请商户看不到邀请人的任何数据。

第二期（`ReferralIntegrationTest` 已覆盖，银行卡核验用模拟结果）：

- 未实名不能绑卡；核验用实名里的姓名和身份证号；卡号只存密文；不一致满 3 次被限；核验不可用返回 503。
- 没绑卡、不勾协议、不满 100 元不能提现；同时只能有一张待审核提现单；冻结中的返利不带走。
- 只有平台运营能看提现单、查看收款信息（留审计）、驳回、登记打款；代扣税超过提现金额、打款日期晚于今天被拒。
- 驳回后返利回到可提现；打款后返利变为已提现，实发 = 提现金额 − 代扣税额。
- 待审核单里的返利不能作废；冻结中的作废不算欠款；已提现的作废变成欠款，欠款让可提现不满 100 元时不能提，下一次提现扣回后欠款清零。

还没验证：

- 微信登录跳转后仍能带上邀请码（前端已实现，需在真实微信回调里走一遍）。
- 阿里云银行卡四要素核验的真实调用（需要账号开通银行卡核验并有余量）。
